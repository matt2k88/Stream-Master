# Ultra Cast v3 — performance changes to apply in Replit

These changes were written and built outside Replit (locally, against the GitHub zip) and are
confirmed working on a real phone and on a Fire TV Stick. They are **app-code changes only**, so
they belong in the Replit project. Nothing here is specific to how the APK is built.

Apply all five. They are independent of each other except where noted.

**Do not change `minSdkVersion`, the ABI/architecture settings, or anything about signing.** Those
live in the local build script, not in this repo — see the last section.

---

## 1. Theme artwork: PNG → WebP (saves ~25MB of APK)

`assets/images/themes/` holds 25 PNGs at 1024×1024, 27.6MB total. As WebP at quality 90 they are
2.8MB — a 90% saving with no visible difference. They are bundled into every build via `require()`
in `client/constants/themes.ts`, so this saving applies whether the APK is built locally or on EAS.

Run this once from the project root (Pillow is in Replit's Python environment; `pip install pillow`
if not):

```python
from PIL import Image
import pathlib

for png in sorted(pathlib.Path("assets/images/themes").rglob("*.png")):
    Image.open(png).convert("RGBA").save(png.with_suffix(".webp"), "WEBP", quality=90, method=6)
    png.unlink()
```

Then update the 25 `require()` paths in `client/constants/themes.ts` from `.png` to `.webp`:

```bash
sed -i 's|\(assets/images/themes/[a-z]*/[A-Za-z]*\)\.png|\1.webp|g' client/constants/themes.ts
```

Verify afterwards: `grep -c '\.webp' client/constants/themes.ts` should print `25`, and
`grep -c 'themes/.*\.png' client/constants/themes.ts` should print `0`.

> **Note for whoever maintains the themes feature:** `getIcon()` in
> `client/contexts/ThemeContext.tsx` is never called anywhere in the app — nothing currently renders
> these theme icons. They are kept (not deleted) on the assumption the feature is half-wired.

## 2. Stop the theme from remounting the whole app

**The bug:** `ThemeProvider` wrapped its children in `<React.Fragment key={themeKey}>`, and it sits
above `AuthProvider` and `DataProvider`. `themeKey` is set asynchronously **twice** on every launch
(once from the AsyncStorage cache, once from `/api/app-theme`). Each change swapped the Fragment key,
which unmounted and remounted the entire tree below it — re-running `checkAuth` and triggering a
**full library re-sync from scratch**. Pull-to-refresh on Home did it again mid-session.

The remount exists only to flush styles that captured the old accent colour at import time. Moving
that boundary *below* the expensive providers keeps the visual refresh and drops the cost.

### 2a. `client/contexts/ThemeContext.tsx`

Replace the final `return` of `ThemeProvider`:

```tsx
// BEFORE
  return (
    <ThemeContext.Provider value={value}>
      <React.Fragment key={themeKey}>{children}</React.Fragment>
    </ThemeContext.Provider>
  );

// AFTER
  // NOTE: no `key` on the children here. This provider sits above AuthProvider
  // and DataProvider, so re-keying it on themeKey tore those down too — and
  // because themeKey is set asynchronously twice on launch (cached value, then
  // the server's), every cold start re-ran checkAuth and re-synced the entire
  // library from scratch. Pull-to-refresh did it again mid-session.
  //
  // The remount is only there to flush styles that captured the old accent, so
  // it now lives on the screen tree instead (see ThemedRootNavigator in App.tsx),
  // which is below the providers that hold the expensive state.
  return <ThemeContext.Provider value={value}>{children}</ThemeContext.Provider>;
```

### 2b. `client/App.tsx`

Change the import:

```tsx
import { ThemeProvider, useAppTheme } from "@/contexts/ThemeContext";
```

Add this component immediately above `export default function App() {`:

```tsx
// Remounting the screen tree is how a theme swap flushes styles that captured
// the previous accent colour at import time. That `key` used to live on
// ThemeProvider's children — above AuthProvider and DataProvider — so each of
// the two async theme sets on launch destroyed auth state and forced a full
// library re-sync. Keeping the boundary here, below those providers, preserves
// the visual refresh without throwing away anything expensive.
function ThemedRootNavigator() {
  const { themeKey } = useAppTheme();
  return <RootStackNavigator key={themeKey} />;
}
```

and use it in place of `<RootStackNavigator />` inside `<NavigationContainer>` (see §3 for the
final shape of that block).

## 3. Start auth during the intro, but keep screens unmounted until it ends

**The problem:** the whole provider tree used to live inside the `introComplete` ternary, so auth
and the library sync did not even *start* until the intro video finished — the one moment the user
is happy to wait was spent doing nothing.

**The catch (found on Fire TV, invisible on phones):** simply mounting everything behind the intro
broke profile selection. On Android TV the D-pad still moves focus into screens that are merely
*covered* rather than unmounted, so pressing OK to skip the intro activated whichever profile card
was focused underneath and reset straight to Home — the profile picker appeared to be skipped.

The fix keeps the providers mounted (that is where the startup time is) but holds back the
**screens** until the intro is done, so nothing focusable exists underneath the overlay.

In `client/App.tsx`, the render block becomes:

```tsx
  return (
    <ErrorBoundary>
      <QueryClientProvider client={queryClient}>
        <SafeAreaProvider>
          <GestureHandlerRootView style={styles.root}>
              <ThemeProvider>
              <AuthProvider>
                <DataProvider>
                  {/* ... all the other providers, unchanged ... */}
                            <SideMenuProvider>
                              {/* Screens wait for the intro, the providers above do not.
                                  Auth and the library sync still run while the video
                                  plays (that is where the startup time goes), but no
                                  screen is mounted underneath the overlay — on Android
                                  TV the D-pad could move focus into a hidden screen, so
                                  pressing OK to skip the intro selected whichever
                                  profile card happened to be focused and jumped
                                  straight to Home. */}
                              {introComplete ? (
                                <>
                                  <NavigationContainer ref={navigationRef}>
                                    <ThemedRootNavigator />
                                  </NavigationContainer>
                                  <StatusBar style="light" hidden={false} />
                                  <MessagePopup />
                                  <MatchReminderOverlay />
                                  <SideMenuDrawer />
                                </>
                              ) : null}
                            </SideMenuProvider>
                  {/* ... closing tags, unchanged ... */}
                </DataProvider>
              </AuthProvider>
              </ThemeProvider>

            {/* The intro now sits ON TOP of a live app rather than replacing it. */}
            {!introComplete && <IntroOverlay onDone={handleIntroDone} />}
          </GestureHandlerRootView>
        </SafeAreaProvider>
      </QueryClientProvider>
    </ErrorBoundary>
  );
```

The only structural edits are: the `{!introComplete ? (...) : (` wrapper is removed from around
`<ThemeProvider>`; the navigator block is wrapped in `{introComplete ? (<>…</>) : null}`; and
`{!introComplete && <IntroOverlay onDone={handleIntroDone} />}` is added as the last child of
`<GestureHandlerRootView>`.

## 4. Hold the library sync until the intro finishes (fixes the laggy Skip button)

**The problem:** with the providers mounted during the intro, the catalogue sync ran behind the
video. Parsing those responses (tens of thousands of rows) blocks the JS thread — the same thread
that moves D-pad focus — so the Skip button went sluggish exactly when people reached for it.

Auth is cheap and still runs during the intro. Only the expensive work waits.

### 4a. New file: `client/lib/intro-gate.ts`

```ts
import { useSyncExternalStore } from "react";

// A one-way "the intro has finished" flag.
//
// The provider tree mounts while the intro video plays so auth can get going
// early, but the library sync must NOT run then: parsing the catalogue
// responses (tens of thousands of rows) blocks the JS thread, and that is the
// same thread that moves D-pad focus — so the Skip button went sluggish on TV
// exactly when people were reaching for it.
//
// A module-level flag rather than a context, because DataProvider sits a dozen
// providers deep and nothing else needs to re-render when this flips.
let introDone = false;
const listeners = new Set<() => void>();

export function markIntroDone(): void {
  if (introDone) return;
  introDone = true;
  for (const listener of listeners) listener();
}

export function useIntroDone(): boolean {
  return useSyncExternalStore(
    (listener) => {
      listeners.add(listener);
      return () => listeners.delete(listener);
    },
    () => introDone,
    () => introDone,
  );
}
```

### 4b. `client/App.tsx`

```tsx
import { markIntroDone } from "@/lib/intro-gate";
```

```tsx
  const handleIntroDone = useCallback(() => {
    setIntroComplete(true);
    // Releases the library sync (see lib/intro-gate.ts) — it is deliberately
    // held back while the video plays so parsing the catalogue cannot stall
    // the JS thread that drives focus movement onto the Skip button.
    markIntroDone();
  }, []);
```

### 4c. `client/contexts/DataContext.tsx`

```tsx
import { useIntroDone } from "@/lib/intro-gate";
```

Add above the sync effect, and gate both effects on it:

```tsx
  // Held until the intro finishes: parsing the catalogue blocks the JS thread,
  // which is what moves D-pad focus, so syncing behind the video made the Skip
  // button sluggish on TV. Auth still runs during the intro — it is cheap — so
  // the sync can start the instant the video ends.
  const introDone = useIntroDone();

  useEffect(() => {
    if (isAuthenticated && introDone && !hasData && !syncRunning.current) {
      sync();
    }
    // ... the !isAuthenticated reset block is unchanged ...
  }, [isAuthenticated, introDone]);

  useEffect(() => {
    if (isAuthenticated && introDone && userInfo?.user_info?.username) void loadCinema();
    // ... cleanup unchanged ...
  }, [isAuthenticated, introDone, userInfo?.user_info?.username, loadCinema]);
```

## 5. Stop freezing when Search / Movies / Series open

**The problem:** `SearchScreen` and `ContentListScreen` each built their own `{ s, n }` index with a
`useMemo`. `useMemo` runs on **first render**, so opening any of those screens normalised the entire
catalogue (NFD normalise + two regexes + lowercase, per title, across tens of thousands of titles)
before the screen could paint — even if the user never typed. This was the worst stall in the app.

The fix caches each normalised title against the stream object itself, shared by every screen,
computed at most once, and warmed in background slices after sync.

### 5a. `client/lib/search.ts` — append to the end of the file

```ts
// Per-stream cache of the normalised title, keyed by the stream object itself.
//
// Screens used to build their own `{ s, n }` index with a useMemo that ran on
// FIRST render — so opening Search / Movies / Series normalised the entire
// catalogue before anything could paint, even if the user never typed.
//
// A WeakMap keyed on the stream object means the work is done at most once per
// stream for the life of the catalogue, is shared by every screen, costs no
// extra allocation per screen, and entries disappear with the streams on
// re-sync. DataContext warms it in the background after sync (see warmSearchIndex)
// so the first search is already instant; if an entry is missing we just compute
// it on demand, so correctness never depends on the warming having run.
const normalisedNames = new WeakMap<object, string>();

export function normalisedName(item: { name?: string | null }): string {
  const cached = normalisedNames.get(item);
  if (cached !== undefined) return cached;
  const n = normaliseSearch(item?.name ?? "");
  normalisedNames.set(item, n);
  return n;
}

// Populates the cache in small slices, yielding to the event loop between them
// so a 60k-item catalogue never blocks a frame. Safe to call repeatedly.
export function warmSearchIndex(lists: { name?: string | null }[][]): void {
  const queue: { name?: string | null }[] = [];
  for (const list of lists) if (list?.length) queue.push(...list);
  if (!queue.length) return;

  let i = 0;
  const CHUNK = 2000;
  const step = () => {
    const end = Math.min(i + CHUNK, queue.length);
    for (; i < end; i++) normalisedName(queue[i]);
    if (i < queue.length) setTimeout(step, 0);
  };
  setTimeout(step, 0);
}
```

### 5b. `client/screens/SearchScreen.tsx`

Import `normalisedName` alongside `normaliseSearch`, then **delete** the three `normLive` /
`normMovies` / `normSeries` memos entirely and replace the `results` memo with:

```tsx
  // which DataContext warms in the background after sync. Building a local
  // `{ s, n }` index here instead used to normalise the WHOLE catalogue on this
  // screen's first render — a multi-second freeze on large libraries before the
  // search box could even paint.
  const results = useMemo(() => {
    if (!trimmed) return { live: [], movies: [], series: [] };
    const pick = <T extends { name: string }>(arr: T[]) => {
      const out: T[] = [];
      for (const s of arr) {
        if (normalisedName(s).includes(trimmed)) {
          out.push(s);
          if (out.length >= RESULT_LIMIT) break;
        }
      }
      return out;
    };
    return {
      live: pick(liveStreams),
      movies: pick(vodStreams),
      series: pick(seriesList),
    };
  }, [trimmed, liveStreams, vodStreams, seriesList]);
```

## What is NOT in this file, and why

The APK size work is **build configuration, not app code**, so it cannot live in this repo and is
applied by the local build script every time instead:

- **Architecture stripping** — the app ships two APKs: 64-bit (`arm64-v8a`) for phones and tablets,
  and 32-bit (`armeabi-v7a`) for Fire TV and older boxes. The universal build was 280MB; these are
  88MB and 78MB. x86/x86_64 are emulator-only and are dropped entirely.
- **Signing** — both are signed with the original EAS upload keystore, so they install over existing
  installs.

If a future build is ever done on EAS instead, those APKs will be ~280MB again unless the same
architecture filtering is added there. The app code in this file is unaffected either way.
